CDS–APDS Link Profile

The Curb Data Specification describes the curb. The APDS standard describes the garage. This profile keeps them as two separate standards and links them only where the curb meets the facility, using fields both specifications already have.

The worked example used throughout: three curb zones on Main St in front of the Civic Garage. Every record shown exists in examples/ and validates against its official schema.

Two domains, one seam

Each specification stays fully usable on its own. Nothing here changes either standard, adds required fields, or asks one side to understand the other's data model. For every real-world object there is exactly one source of truth.

CDS 1.1 · on-streetAPDS 4.1 · off-street
DomainThe public curbGarages, surface lots and other facilities

APDS can model on-street parking too. This profile doesn't use it that way: the curb is described once, in CDS.

There is also no session hand-off. A car leaving the curb and entering the garage creates two independent records, because correlating them would mean tracking individual vehicles.

The three touchpoints

T1

Access

A facility entrance sits on a curb, usually behind a no-stopping apron.

Curb Zone↔VehicularAccess
T2

Nearby supply

The curb is full, so show the garages nearby with their live capacity.

Curb Area↔Place
T3

Shared permits

One permit programme is honoured at the curb and inside a facility.

Curb Policy→RightSpecification

How a link is written

Both specifications already have a field for pointing at an external record. The profile only fixes how to fill it in.

CDS external_references

"external_references": [{
  "name": "APDS",
  "reference_url": "https://apds.example.org/v4/places/…f002",
  "identifier_name": "HierarchyElement.id",
  "ids": ["…f002"],
  "public": false
}]

Available on Curb Areas, Zones, Spaces, Objects and Policies. Adding a link never forces a new curb_zone_id.

APDS operatorDefinedReference

"operatorDefinedReference": {
  "id": "…b001",
  "version": 1,
  "className": "CdsCurbZone"
}

Available on every HierarchyElement. className must match ^[A-Z]+[A-Za-z0-9]+, so cds:CurbZone is invalid. version is always 1, because CDS objects are unversioned.

Link kindCDS recordAPDS recordDeclared in
accessCurb Zone, Curb ObjectHierarchyElement, type: vehicularAccessBoth sides
supplyCurb Area, Curb ZoneHierarchyElement, type: placeBoth sides
permitCurb PolicyRightSpecificationCDS only (RightSpecification has no reference field)

A link declared on both sides is confirmed, and one declared on a single side is one-sided. Both are valid; confirmation just makes stale data detectable. operatorDefinedReference holds one value, so a garage with several entrances declares one link per VehicularAccess.

T2 · Nearby off-street supply

T3 · Shared permits

A CDS Policy whose rule is limited to permit holders points at the APDS RightSpecification that defines the programme. Enforcement then asks APDS whether the vehicle it sees holds that permit.

sequenceDiagram
  participant Enf as Curb enforcement
  participant CDS as CDS Curbs API
  participant APDS as APDS API
  Enf->>CDS: GET zone, then its policies
  CDS-->>Enf: rule user_classes [permit] + reference to rights/specs/{id}
  Enf->>APDS: GET /rights/assigned?right_spec={id}&credential_id=ZA-004217
  APDS-->>Enf: AssignedRight (issuanceTime, expiry)
  Enf->>APDS: GET /rights/specs/{id}
  APDS-->>Enf: validity (status, overall period)
  Note over Enf: valid · expired · not_yet_valid · programme_inactive

A permit is valid at time t when a returned right belongs to a linked programme, holds the presented credential (ignoring case, spaces and hyphens), and satisfies issuanceTime ≤ t < expiry, and the programme itself is neither suspended nor planned and is inside its overall period. Whether the curb policy applies at t is still decided by CDS logic, as it is today.

Privacy. Plates and permit numbers are personal data in many jurisdictions. Send them only to answer a verification request, never log them, and don't echo them back. The reference service returns ZA-***217.

Reference link service

Optional. Everything above works with the two standard APIs alone. The service provides the reverse index permits need, detects broken links, and answers T2 and T3 in one call each. It keeps no parking data of its own.

Upstream schema issues found

Found while validating the examples. The validator patches them in memory and prints them on every run. The APDS issue is reported as parkingdata/spec#33; the CDS issues are not yet reported.

SpecLocationIssue
APDS 4.1schemas/ReferenceRequires id and className but sets maxProperties: 1, so no instance can validate. This affects credential identifiers.
CDS 1.1geoJSON_polygon.yamlPolygon coordinates is modelled as one list of positions (a LineString shape) instead of an array of RFC 7946 rings.
CDS 1.1coordinates.yamlDescribes positions as latitude, longitude; RFC 7946 order is longitude, latitude.
